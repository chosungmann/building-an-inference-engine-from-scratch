# 다음 판에서 다룰 내용

이번 판에서 의도적으로 미룬 내용을 모아 둡니다. 미룬 이유와, 다음 판에서
다루려면 무엇이 필요한지를 함께 적습니다.

이번 판의 원칙은 "저자의 맥(Apple M4 Max)에서 실행하고 측정한 것만
싣는다"입니다. 시뮬레이터와 에뮬레이터로 확인할 수 있는 것은 이번 판에
넣고, 실제 기기나 다른 하드웨어가 있어야만 측정할 수 있는 것은 여기로
옮깁니다.

## 실제 기기 측정

| 항목 | 이번 판에서 하는 것 | 다음 판으로 미루는 것 | 필요한 것 |
|---|---|---|---|
| 아이폰 | 시뮬레이터에서 빌드, 앱 연동, 출력 정확성 확인 | 실기기의 속도, 메모리, 발열, 전력, NPU(Neural Engine) 성능 | 아이폰 테스트 기기 (보유) |
| 안드로이드폰 | 에뮬레이터에서 빌드, 앱 연동, 출력 정확성 확인 | 실기기의 속도, 메모리, 발열, 전력, 모바일 GPU와 NPU 성능 | 안드로이드 테스트 기기 (보유) |
| 모바일 추론 엔진 대결 (LiteRT, NCNN, MNN) | 맥에서 설계 비교와 실측 | 폰의 CPU와 GPU에서의 실측. 기기에 따라 순위가 달라지는지 확인 | 위 두 기기 |
| 온디바이스 LLM | 메모리 예산 계산, 맥에서의 실행 | 폰에서의 초당 토큰 수와 지속 성능 | 위 두 기기 |

시뮬레이터와 에뮬레이터는 맥의 CPU와 GPU로 실행되므로, 여기서 잰 속도는
폰의 성능을 대표하지 않습니다. 그래서 이번 판에서는 동작 확인에만 쓰고
성능 수치는 싣지 않습니다.

## 다른 하드웨어에서의 측정

| 항목 | 이번 판에서 하는 것 | 다음 판으로 미루는 것 | 필요한 것 |
|---|---|---|---|
| x86-64 (AVX2, AVX-512) | 코드 작성, GitHub Actions에서 정확성 테스트 | 성능 측정과 Apple Silicon과의 비교 | 클라우드 x86 서버 |
| NVIDIA GPU 엔진 (TensorRT-LLM, vLLM, SGLang) | 설계 분석 | 실측 비교 | 클라우드 GPU 서버 |
| 데이터센터 규모 기법 (모델 병렬화, 프롬프트 처리와 생성의 분리, 캐시 인지 라우팅, 오토스케일링) | 설계 분석 | 여러 GPU와 여러 서버에서의 실습과 측정 | 클라우드 GPU 서버 여러 대 |
| 기계별 순위 차이 | 맥 한 대의 결과 | 여러 기계의 결과를 나란히 놓은 분석 | 위 장비 전부 |

## 실제 운영 환경에서 쓰이는 추론 엔진

저자의 바람입니다. 다음 판에는 실제 서비스에서 쓰이는 추론 엔진의 내용을
충실히 담습니다. 이번 판은 엔진을 직접 만드는 데 집중했고, 운영 환경의
엔진은 5부에서 소스와 문서를 읽은 것이 전부입니다. 견준 상대도 llama.cpp의
서버 하나였습니다([53장](../book/src/part7/ch53_scorecard.md)의 "재지 못한
것").

| 항목 | 이번 판에서 하는 것 | 다음 판에서 다룰 것 | 필요한 것 |
|---|---|---|---|
| vLLM, SGLang, TensorRT-LLM | 소스와 문서를 읽고 설계를 설명 | 직접 띄워 같은 모델과 같은 부하로 측정. 설정이 처리량과 지연을 어떻게 바꾸는지, 엔진마다 스케줄러와 KV 캐시 관리가 어떻게 다른지 | 클라우드 GPU 서버 |
| 서빙 계층 (Triton Inference Server, KServe, Ray Serve 같은 것) | 다루지 않음 | 엔진 위에서 모델을 올리고 내리고 라우팅하는 계층이 무엇을 하는지. 어느 것을 다룰지는 조사해서 정함 | 클라우드 GPU 서버 여러 대 |
| 운영에서 보는 것 | 5부에서 개념과 작은 실험 | 실제 엔진이 내놓는 지표, 과부하에서의 동작, 모델 교체, 장애 때의 동작 | 위와 같음 |
| x86 서버의 CPU 추론 (OpenVINO, ONNX Runtime) | ONNX Runtime만 맥에서 측정 | x86에서 AVX-512와 VNNI를 쓰는 엔진과 우리 엔진의 비교 | 클라우드 x86 서버 |
| 폰에서 실제로 쓰이는 경로 (LiteRT, Core ML, ExecuTorch, 운영체제 내장 모델) | 맥과 시뮬레이터에서 확인 | 실기기에서의 측정 ("실제 기기 측정" 표) | 테스트 기기 (보유) |

어느 엔진이 "실제로 쓰이는가"는 판마다 다시 확인해야 합니다. 위의 이름은
이번 판을 쓰는 시점(2026년 11월)의 후보이고, 다음 판을 시작할 때 조사부터
합니다.

## 컴파일러 쪽 기술

[52장](../book/src/part7/ch52_ml_compilers.md)은 작은 컴파일러를 만들고 WebLLM이
받는 셰이더를 읽는 데서 멈췄습니다. TVM과 MLIR은 논문의 초록과 문서로만
설명했고, 돌려 보지 않았습니다.

| 항목 | 이번 판에서 하는 것 | 다음 판에서 다룰 것 |
|---|---|---|
| MLIR | 문서로 알려진 내용을 한 절로 설명 | 방언을 직접 정의해 보거나 IREE, Torch-MLIR로 모델 하나를 컴파일해, 낮추는 단계마다 표현이 어떻게 바뀌는지 봅니다. [52장](../book/src/part7/ch52_ml_compilers.md)의 세 층짜리 컴파일러와 나란히 놓습니다. |
| Mojo와 Modular의 추론 엔진 | 다루지 않음 | 저자가 궁금해하는 기술입니다. 언어와 엔진이 MLIR 위에서 무엇을 하는지, 이 책의 엔진과 견줄 수 있는 것이 무엇인지부터 조사합니다. 이번 판을 쓰면서 확인한 사실이 없으므로 여기에는 주제만 적습니다. |
| TVM의 자동 튜닝 | 논문의 초록까지 읽음 | 모델 하나를 직접 컴파일하고 튜닝해 [52장](../book/src/part7/ch52_ml_compilers.md)의 스물네 가지 찾기와 견줍니다. |

## 초고에서 덜 된 것

하드웨어나 주제의 문제가 아니라, 이번 판의 본문에서 덜 된 것입니다.

- **근거의 재확인.** 논문은 대부분 초록까지만 읽었고, 각주를 저자가 다시
  열어 확인하지 않았습니다([부록 F](../book/src/appendix/f_references.md)의 F.5절).
- **통독.** 문체와 용어를 책 전체에서 고쳤지만, 처음부터 끝까지 사람이
  읽으며 다듬지는 않았습니다.
- **읽는 경로.** 쉰세 장을 다 읽지 않는 독자를 위한 안내가 없습니다. 1~3부만
  읽어도 닫히는지, 분야별로 골라 읽을 수 있는지를 확인하고 서문에 적습니다.
- **계산 전체를 GPU에.** 선형 층만 GPU에 올렸습니다. 53장의 격차 분류에서
  가장 큰 갈래입니다.
- **품질의 측정.** 객체 검출의 정확도, 받아쓰기의 낱말 오류율, 합성한
  소리의 품질은 기준 구현과 같다는 것까지만 확인했습니다.

## 해마다 갱신할 때 할 일

이 책은 연도를 붙인 판으로 냅니다. 첫 판이 2026년판이고, 해마다 11월 무렵에
다음 해의 판으로 갱신합니다. 원리를 다루는 본문은 그대로 두고, 그 해의
기록에 해당하는 것을 다시 만듭니다.

| 할 일 | 대상 | 방법 |
|---|---|---|
| 비교 엔진의 버전을 올린다 | [부록 B](../book/src/appendix/b_engines.md)의 엔진 전부 | 그 시점의 최신 릴리스로 고정한다. 부록 B.8절의 순서대로, 답이 같은지 먼저 확인하고 벤치마크를 돌린다 |
| 소스를 읽은 각주를 릴리스에 맞춘다 | 다른 엔진의 소스를 인용한 각주 전부 | 잰 것과 같은 릴리스의 태그에서 파일과 줄 번호를 다시 확인한다. 2026년판은 그날의 커밋에서 읽은 곳이 많다. 릴리스가 없는 저장소는 커밋을 고정하고 그렇다고 적는다 |
| 측정값과 그림을 다시 만든다 | 장마다의 표와 그림, [53장](../book/src/part7/ch53_scorecard.md)의 성적표 | `scripts/bench_chNN.sh`와 `scripts/figures/chNN.py` |
| 브라우저의 지원 표를 다시 확인한다 | 48~50장 | 측정 페이지를 그 해의 브라우저 넷에서 연다. 가장 빨리 낡는 대목이다 |
| 모델을 다시 고른다 | 책이 쓰는 모델 전부 ([부록 C](../book/src/appendix/c_models.md)) | 그 해에 같은 크기에서 널리 쓰이는 모델로 바꿀지 정한다. 바꾸면 기준 답도 다시 만든다 |
| "실전 엔진에서는" 절을 다시 읽는다 | 모든 장 | 엔진이 그 사이에 바꾼 것, 새로 널리 쓰이게 된 엔진을 반영한다 |
| 문서와 명세에서 인용한 사실을 다시 확인한다 | 각주에 읽은 날짜를 적은 곳 | 운영체제의 한도, 앱 가게의 크기 한도, 표준의 단계처럼 바뀌는 것 |
| Rust와 도구의 버전을 올린다 | [부록 A](../book/src/appendix/a_rust.md), CI | 안정판에 새로 들어온 기능(예: `f16`, SME 내장 함수)으로 코드를 줄일 수 있는지 본다 |
| 이 문서의 표에서 한 것을 지운다 | 이 문서 | 그 해에 채운 빈칸을 옮기고, 새로 미룬 것을 적는다 |

해가 바뀌는 사이에 숫자가 크게 달라지면 판을 기다리지 않고 사이트의 그
장만 고칩니다. 그때는 고친 날짜를 그 장에 적습니다.

## 다음 판을 위해 이번 판에서 지킬 것

- 벤치마크는 명령 하나로 다른 기계에서도 그대로 실행되게 만듭니다.

- 본문에서 실측하지 않은 대목은 그렇다고 표시해, 다음 판에서 채울 자리를
  찾기 쉽게 합니다.
